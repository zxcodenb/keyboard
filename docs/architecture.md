# 目录与扩展边界

## 依赖方向

```text
cmd/desktop                 选择档案、组装适配器、确定用户路径、管理窗口生命周期
├── internal/desktop        只把界面需要的方法暴露给桌面框架
│   └── internal/app        接管状态、预设、配置、重连与发送循环
│       ├── internal/lighting   设置验证与灯效计算
│       └── internal/keyboard   通用数据与适配器接口
├── internal/adapters       具体协议实现，只依赖通用键盘数据
└── profiles                嵌入键盘档案，提供布局和灯珠位置

apps/desktop/frontend       使用生成的接口调用控制器，使用活动档案渲染键盘
```

应用层不导入任何具体适配器；灯效层不知道设备标识、报告长度、字节顺序或固定键位数量。桌面框架和系统权限入口只出现在桌面层。旧脚本没有进入运行时依赖链。

## 各层负责什么

- **键盘档案**：稳定标识、显示名称、连接说明、键帽几何、区域划分、灯珠索引与流光位置。后端与浏览器示例共用同一份数据，不再各自维护型号键位表。
- **灯效层**：把设置、时间和档案中的灯珠位置转换为颜色帧。索引是标识，不假设索引连续、单字节或等于固定列号公式。
- **适配器层**：发现和打开设备，编码颜色帧，限制报告长度及发送速率，处理底层设备句柄。当前单字节索引限制只存在于当前接收器适配器中。
- **应用层**：校验当前档案允许的灯珠索引，管理设置、预设和接管状态，保持发送串行化，处理断开重连。只有原子保存成功后才提交内存状态。
- **桌面层**：绑定前端接口、打开系统权限设置。适配器生命周期不会暴露为前端可调用的方法。

## 用户与配置边界

桌面入口从系统当前用户的数据目录取得根路径，再组装：

```text
users/<用户工作空间标识>/keyboards/<键盘档案标识>/lighting.json
```

控制器只接收自己的配置路径，不读取全局用户，也不自行选择型号。当前入口固定使用本地工作空间和唯一已实现的适配器；后续登录或工作空间选择应在入口／会话管理层完成，而不是塞进灯效算法。

旧配置兼容路径只给默认工作空间和原键盘传入；其他控制器不传兼容路径。旧配置在首次保存到新位置之前不做破坏性移动。

当前不是多租户服务，路径分区也不是登录认证或访问控制。后续若引入来自外部的用户标识，必须在身份边界验证并生成安全的路径标识，不能直接拼接用户输入。同型号多设备应另行引入设备实例标识，不能把显示名称当作实例标识。

## 接入下一款键盘

1. 在 `profiles/` 增加档案，描述真实布局、可控制灯珠和位置；不要猜测未验证的键位。
2. 在 `internal/adapters/` 下新增适配器，实现 `keyboard.Driver` 与 `keyboard.Device`。若确实复用同一种协议，可在该协议适配器内复用编码，不把型号判断散布到应用层。
3. 在桌面入口选择档案并组装相应适配器，传入独立的用户／键盘配置路径。后续有第二个适配器且需要用户选择时，再增加目录注册和选择界面。
4. 为新适配器补充协议字节、事务上限、断开重连和释放测试，再做实机验证。新档案本身不代表新设备已经适配成功。

当前只管理一个活动适配器，不实现插件系统、自动驱动下载、多设备并发或账号服务。以后需要多设备同时控制时，应增加统一设备管理器，集中管理底层通信库的进程级生命周期、枚举和线程归属；不能直接并行启动多个会各自初始化／退出共享底层库的控制器。

## 构建边界

- 原生后端只有仓库根目录一个 `go.mod`，模块名为 `lightstudio`。
- 桌面配置留在 `apps/desktop/`，入口指向 `../../cmd/desktop`。
- 界面源码在 `apps/desktop/frontend/`，生成绑定也写入该目录。
- `profiles/` 数据嵌入原生程序；界面只为浏览器预览静态导入示例档案，原生模式从控制器快照取得活动档案。
- 编译生成绑定不会进入窗口就绪回调，因此不会启动设备循环。
- `tools/legacy/`、用户数据、虚拟环境和原始标定记录都不进入应用包。
